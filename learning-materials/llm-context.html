大模型的上下文（Context）

Context / Context Window / 上下文窗口
领域：人工智能 / 大语言模型 目标读者：初学者 深度：入门到进阶 检索日期：2026-09-05

1个人解释

想象你和 AI 在一块大小固定的黑板上对话：你写的提问、AI 写的回答、之前所有的聊天记录，都只能写在这块黑板上。黑板写满之后，为了写下新内容，最早写在角落里的内容就会被擦掉——AI 也就"忘记"了那部分。这块黑板就是上下文（Context），黑板的大小就是上下文窗口（Context Window）。

模型每次回答问题前，能"看到"的只有黑板上现存的内容——包括系统设定、对话历史、你贴给它的资料、工具返回的结果。不在黑板上的东西，它一概不知道。（类比仅在"容量有限、旧内容被覆盖"这一点上成立；黑板是真正擦除，而模型实际是按 Token 截断输入。）

2核心机制

计量单位：Token（词元）

上下文的容量不用"字数"衡量，而用 Token——模型处理信息的最小语义单元。粗略换算：中文约 1.5–2 个汉字占 1 个 Token，英文约 0.75 个单词占 1 个 Token；标点、空格甚至表情符号也会占用 Token。

窗口的精确定义

上下文窗口（Context Window）：基于 Transformer 架构的大语言模型一次可以处理的最大序列长度，即模型生成下一个 Token 时能够回顾和参考的前文 Token 数量上限。输入（Prompt）和输出（Output）共享这一空间。

窗口里装着什么

  • 系统提示词：给模型的角色设定和规则，常驻窗口。
  • 对话历史：本次会话中此前的问答。
  • 参考资料：用户贴入的文档、检索（RAG）回来的片段、工具调用的返回结果。

上限由什么决定

  • 位置编码：Transformer 本身不感知顺序，需要位置编码（如主流的 RoPE）给每个 Token 标"位置"；训练时见过的序列长度设定了理论上限，超出后需依赖插值等外推技巧。
  • 计算成本：标准注意力机制的计算和显存开销随序列长度呈平方级（O(n²)）增长，长上下文意味着更贵、更慢。
  • 有效记忆：窗口塞得下 ≠ 用得好。真正能被模型理解并利用的信息量（有效记忆）通常远小于窗口标称值。

发展现状

窗口大小呈指数级增长：早期 GPT-3.5 只有 4K Token；GPT-4o、Llama 3.1 等达到 128K；Claude 约 200K；Gemini 1.5 Pro 支持 100 万–200 万 Token。窗口变大之后，配套的"上下文工程"（只把相关信息放进窗口）成为新的核心课题。

3应用场景

  • 长对话的记忆管理：多轮对话越聊越长，工程师用"滑动窗口"（只保留最近 N 轮）或"摘要压缩"（定期把早期对话总结成短文）控制窗口占用，防止用户发现 AI"失忆"。
  • 长文档处理：合同审查、论文分析等任务文档动辄上百页。直接塞满窗口既贵又慢，工程上的标准做法是分块（Chunking）+ 按需检索（RAG），只把相关片段放进窗口。
  • Agent 的状态管理：Agent 的任务状态、中间结果、工具返回都挤在同一个窗口里，需要按优先级裁剪——系统指令永不被裁，闲聊记录最先被清理。
  • 成本与延迟控制：模型按输入/输出 Token 计费，窗口内容越精简，单次调用越便宜、响应越快；行业估计管理不善的系统会浪费 60–80% 的窗口空间。
典型失效情况：对话或文档超出窗口上限时直接报错（"context length exceeded"）；即使没超限，关键信息若淹没在大量无关内容中，模型注意力被稀释，也会"看不见"重点。

4边界辨析

对比A 是……B 是……
上下文窗口 vs 上下文长度实际预测时模型考虑的输入序列长度，随输入变化模型架构能处理的最大序列长度，是理论上限；实际窗口 ≤ 长度上限
上下文 vs 训练知识本次调用时模型"眼前看得到"的信息，随每次对话重新组装训练阶段写进参数里的知识，不会因为对话变长而丢失
上下文 vs 长期记忆短期工作记忆，窗口有限、轮次结束即清空需借助外部存储（如向量数据库）实现的跨会话记忆，按需检索回填窗口

常见误解

  • 误解一：窗口越大，模型记得越牢。窗口大只代表"装得下"，不代表"用得好"。注意力随长度稀释，有效记忆明显小于标称窗口；业界因此强调"上下文是工作记忆，不是存储"。
  • 误解二：上下文 = 模型的记忆。模型没有跨调用的内在记忆——每生成一次回复，都是基于当前窗口内容重新计算。你昨天告诉它的事，今天没出现在窗口里，它就不知道。
