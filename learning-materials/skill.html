1个人解释

大模型像一个博览群书但没进过你们公司的新员工：它知识渊博、能说会道，却不知道你们的报销流程怎么走、周报要按什么格式写。你当然可以每次都在对话里从头解释一遍，但更省事的做法是把"什么时候做、按什么步骤做、做错了怎么处理"写成一份操作手册放进它的抽屉——需要时它自己翻出来照着做。

这份"操作手册"就是 Skill：把做事的方法（know-how）打包成可复用文件的能力单元，核心是一份 SKILL.md 说明文档，附上可选的脚本、参考资料和模板。它填的是"一条提示词太零散、一个工具又太原子"之间的空档（类比仅在"把流程写成文档供按需查阅"这一点上成立；Skill 并不会改变模型本身的知识和能力）。

2核心机制

典型结构

一个 Skill 就是一个文件夹，核心是 SKILL.md：开头是 YAML 元数据（名称 name、描述 description），正文用 Markdown 写工作流程与约束；旁边可放可选资源——scripts/（可执行脚本）、references/（按需加载的参考文档）、assets/（输出时使用的模板、图片等）。

渐进式披露（Progressive Disclosure）

第一层：元数据（name + description，约 100 Token）常驻上下文，供 Agent 判断"要不要用我"。
第二层：SKILL.md 正文（建议少于 5,000 Token）仅在任务命中后才注入上下文。
第三层：脚本、参考文档等资源按需读取或执行，不占常驻空间。

这种三层设计直接解决了"能力越多、系统提示词爆炸"的问题：就算装了一百个 Skill，平时也只有一百条简短摘要待命，命中哪个才加载哪个。

运行流程

  1. 发现：Agent 启动时扫描各 Skill 的元数据建立索引。
  2. 选择：用户任务到来时，Agent 根据描述判断应调用哪个 Skill。
  3. 加载：SKILL.md 正文注入上下文，附带的脚本与资源按需使用。
  4. 执行：按正文指令行动，内部可调用工具、运行脚本，任务完成后卸载正文、只保留元数据。

与 Tool 的本质区别

Anthropic Agent Skills 联合创造者 Barry Zhang 的一句话定义："Skills 是打包了可组合过程性知识的文件集合——说白了，就是些文件夹。"区别在于判断放在哪：Tool 是原子的"执行这个动作"（do_this），一次调用、无内部流程；Skill 是"知道怎么做成一类事"（know_how_to_do_class_K），封装了用哪些工具、按什么顺序、出错怎么办的判断，可编排多个工具调用。

3应用场景

  • 编程助手的能力包：把"按团队规范生成 commit 信息""处理 PDF 提取表格"等固定套路写成 Skill，AI 编程助手在合适时机自动选用，而非每次都靠用户口头交代。
  • 企业流程封装：把内部周报格式、邮件归档规则、报销标准等"模型不可能知道的公司知识"沉淀为 Skill，团队全员共享，新人 Agent 开箱即用。
  • 多 Agent 协作：编排者（Orchestrator）把高级能力作为 Skill 分配给子 Agent；单个 Skill 内部再调用底层工具完成每个步骤。
  • 技能市场：Anthropic 等厂商建立了可分享、可安装的 Skill 生态，用户像装 App 一样给 Agent 增加能力。
典型失效情况：装太多 Skill 会导致选择困惑——面对一堆能力描述相近的 Skill，模型容易选错；Skill 描述写得含糊（如只写"处理文件"）同样会造成误调用。设计原则是给 Agent 完成任务所需的最小技能集。

4边界辨析

对比A 是……B 是……
Skill vs Tool / Function可复用的能力包：封装"何时、为何、如何组合动作"的判断，可包含多步流程原子执行能力：单次函数调用，name + 描述 + 参数 schema，无内部流程
Skill vs Prompt有元数据、触发条件、资源与生命周期，可被检索、加载、复用零散文本片段，无结构、无生命周期，靠人工复制粘贴
Skill vs MCPAgent 内部的能力层：教 Agent 怎么做事外部系统的协议层：规定 Agent 与工具之间怎么连接、怎么发现工具；两者正交，Skill 里可以调用 MCP 工具

适用边界

该用 Skill：某类任务反复出现、做法可沉淀成固定步骤（步骤数可预测但含领域判断）。不该用 Skill：单次性任务（直接写在提示词里）、纯原子操作（注册一个 Tool 即可）、需要跨多个 Skill 的临时编排（那是 Workflow / 编排层的事）。

常见误解

  • 误解一：装了 Skill，模型就"学会"了新知识。不是。Skill 不改变模型参数，只是把指令和资源按需喂给模型——相当于"开卷考试时递上来的参考书"，模型还是原来那个模型。
  • 误解二：Skill 装得越多越强。恰恰相反：能力描述过多会稀释模型的判断力（skill 选择困惑），好的实践是保持最小必要技能集，按实际缺口逐步增加。
